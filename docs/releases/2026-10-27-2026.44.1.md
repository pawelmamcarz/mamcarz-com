## 4. Jak sprawdzić, że deploy nie cofnie produkcji

Przed deployem, na czystym checkoutcie tego commita:

1. `npm run package:site && npm run verify:release`.
2. Pobierz z produkcji wszystkie adresy z `https://mamcarz.com/sitemap.xml` oraz pliki, do których linkują (CSS, JS, obrazy, fonty, `llms.txt`, `llms-full.txt`, `robots.txt`).
3. Znormalizuj pobrane HTML: usuń linię skryptu `static.cloudflareinsights.com/beacon.min.js` wstrzykiwaną przez Cloudflare Web Analytics. W plikach repo usuń znaczniki `<!--email_off-->` i `<!--/email_off-->`, które Cloudflare zdejmuje przy serwowaniu. W obu wersjach zamień token `?v=` na wspólny symbol.
4. Porównaj bajtowo z `.public/`. Oczekiwane różnice są tylko te:
   - `index.html`, `en/index.html`: figura `contact-portrait` w kontakcie i tekst `data-chat-fallback` z PR #20;
   - `aplikacje-operacyjne/index.html`, `en/aplikacje-operacyjne/index.html`: wstęp listy aplikacji i etykieta EN `03 / Products` z PR #20;
   - `assets/css/style.css`: reguły `.contact-portrait`, kolor `.aviation-call-sign` i kontrast etykiet w panelach z PR #20;
   - `sitemap.xml`: `lastmod` 2026-10-27 dla `/`, `/en/`, `/aplikacje-operacyjne/`, `/en/aplikacje-operacyjne/`.
   Każda inna różnica oznacza, że deploy cofnąłby coś z produkcji.
5. Lista tras w `sitemap.xml` musi być równa `PUBLIC_PAGES` (27 dokumentów) i zawierać `/o-mnie/` oraz `/en/o-mnie/`.

Po deployu:

1. `/o-mnie/` i `/en/o-mnie/` zwracają 200, a strony serwują `style.css?v=20261027-flightplan-5` i `main.js?v=20261027-flightplan-5`.
2. Strona główna i `/o-mnie/` wyglądają jak przed deployem, z wyjątkiem zdjęcia w kontakcie.
